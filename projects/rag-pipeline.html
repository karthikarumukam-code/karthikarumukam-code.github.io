What this is

A retrieval-augmented generation pipeline: ask a question, find the most relevant passages in a set of PDF documents, and have a language model answer using only those passages. I built it twice during a bootcamp workshop, first from scratch to see every moving part, then with LangChain, Chroma, HuggingFace embeddings and a hosted open-weight model (gpt-oss on Groq).

Scope. This was a guided workshop, not a production system. It used a small document set, had no user testing and was not deployed. I include it because understanding how RAG works is the base for judging RAG proposals as a project manager.

How the pipeline works

Indexing, done once per document set
  1. 1. Load and cleanPDF text converted to clean, structured text
  2. 2. ChunkSplit into passages small enough to retrieve precisely
  3. 3. EmbedEach chunk becomes a vector with a sentence-embedding model (all-mpnet-base-v2)
  4. 4. StoreVectors and text saved in a Chroma vector database
Answering, done for every question
  1. 5. QuestionThe user's question is embedded the same way
  2. 6. RetrieveThe closest chunks are fetched from Chroma
  3. 7. GenerateThe LLM answers from the retrieved text, not from memory
  4. 8. Answer with sourcesThe reply points back to the passages it used

Why build it from scratch first

A framework hides the decisions that decide quality. Building the loop by hand (chunking, embedding, similarity search, prompt assembly) made the trade-offs concrete: chunks that are too large blur the match, chunks that are too small lose context, and retrieving too few passages starves the model while retrieving too many invites noise. Rebuilding with LangChain then showed what a framework saves and what it abstracts away.

The workshop also covered cleaning PDFs into Markdown, adding source citations to answers, and using an LLM as a judge to evaluate answers.

What I take from it as a project manager

  • RAG quality is largely decided before the language model is involved: document cleaning, chunking and retrieval. Acceptance criteria should test retrieval separately from generation.
  • Citations turn an answer into something a person can check. For any assistant that answers from company documents, I would make them a requirement, not a nice-to-have.
  • An assistant needs a defined moment where it stops and hands over to a person. That is the design principle behind the escalation path in the Aurelia feasibility case.

Limits

  • Small document set and workshop scope: nothing here shows how the pipeline behaves at scale or with messy company documents.
  • No systematic evaluation of retrieval quality beyond the workshop exercises.
  • The hosted model is a third-party service; a real deployment with personal data would need a data-protection review first.

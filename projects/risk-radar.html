AI Project Risk Radar

An early-warning tool that helps a project manager see the latest and combined risks across projects, with the evidence behind each flag, and leaves the decision with the PM.

The problem

A project manager's risk signals live in separate documents: the status report, the RAID log, the dependency register, the plan and the meeting minutes. A compounding risk that spans several of them is often noticed too late to do anything but escalate or absorb an overrun.

The Risk Radar cross-checks those documents and gives the PM an at-a-glance view of the latest and combined risks, so mitigation can be planned with the team and the steering committee can be warned in time.

What it does

  • Reads a project's status reports, RAID log, dependency register, plan and meeting minutes.
  • Flags compounding risks when signals appear across several categories, plus critical or high risks, overdue plan tasks and risks that are new since the last report.
  • Scores each risk with a transparent formula (Probability × Impact × Urgency) and links every flag back to its exact source sentence or table row.
  • Shows the PM's own RAG status next to the tool's assessment and surfaces any disagreement instead of hiding it.
  • Plots a trend across the historical weekly reports and a portfolio view of all projects side by side.

How it is put together

Structured data such as a RAID row or an overdue plan task is parsed once, deterministically, and never touched by an LLM. Only narrative text (status reports, minutes) is re-extracted by a model, and only when one is configured. If the model is unavailable, the tool falls back to a rule-based extractor and shows the reason.

  1. Project documentsStatus reports, RAID log, dependency register, plan, minutes
  2. ExtractionStructured rows: deterministic parsers, always on.Narrative text: rule-based baseline, or an LLM (Anthropic, OpenRouter or Ollama) when configured.
  3. Risk engineCorrelates signals, raises a compound-risk flag across categories, marks new risks
  4. Scoring and recommendationProbability × Impact × Urgency, a recommendation, and the PM's RAG shown beside the AI's read
  5. PM decidesEvery flag carries its evidence. Nothing is sent, written or escalated automatically.

The same code path runs inside the app and inside the offline evaluation harness, so the test results describe the real pipeline, not a mock of it.

How the work progressed

  1. Rule-based baselineA deterministic extractor first, so there was something fair to beat.
  2. LLM extractionAdded as an alternative to the baseline, with Anthropic, OpenRouter and Ollama as providers.
  3. Evaluation harnessA hand-labelled gold set and an offline harness to compare both approaches on the same documents.
  4. MVPA score confrontation between LLM and rules, schedule-hygiene, risk-register-hygiene and reporting-cadence metrics, rolled up into a confidence rating.
  5. Web applicationA React and FastAPI web app on top of the same engine. The Streamlit prototype stayed as a fallback.

How it is evaluated

Evaluation is split into three layers, so a good headline number cannot hide a weak part:

  • Extraction: were the right signals pulled out of the documents?
  • Detection: were the right risks flagged, compared with the baselines?
  • Calibration: does the stated confidence match how often the tool is right?

At the prototype stage (September 2026) the suite had 65 automated tests and 11 of 11 expected risks found on the hand-labelled gold set. That gold set is small and synthetic, so read it as a regression check, not as proof of real-world accuracy.

One design rule

No automated action. The PM decides. The tool synthesises evidence into a recommendation and stops there. It does not write to Jira, send an email or escalate. The guardrail was written into the project roadmap and re-checked at every pull-request review.

How the team ran it

  • A four-phase Kanban board, with the project-manager role rotating every week.
  • Risks tracked as labelled issues, and a mandatory review on every pull request.
  • Six GitHub Actions workflows, including secret scanning, and deterministic tests that mock the LLM so CI never depends on an API.
  • Daily evaluation runs until the hand-in on 12 October 2026.
  • A Responsible-AI review with the outcome “proceed with conditions”.

Limits

  • All data is synthetic. Real project documents name real people, and the privacy and security design for that was out of scope.
  • The tool has not yet been validated with practising project managers. That is the most important next step.
  • Thresholds and heuristics were tuned on a small gold set. They are working defaults, not principled constants.
  • No integration with Jira, Azure DevOps or ServiceNow, and no live monitoring: it only checks when a PM runs it.
